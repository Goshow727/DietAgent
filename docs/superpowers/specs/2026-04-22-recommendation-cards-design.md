# Recommendation Banner Cards — Design Spec
Date: 2026-04-22

## Overview

A personalized banner card stack displayed on the home screen, recommending diet and fitness content based on the user's recent intake/burn logs and body profile. Cards are pre-generated by an LLM-powered pipeline and served from a DB pool. Users can red-cut (left-swipe) individual cards to permanently remove them; new cards are generated asynchronously to maintain the pool.

## 2. Data Model

### `recommendation_cards` table

| column        | type             | notes                                      |
|---------------|------------------|--------------------------------------------|
| `id`          | UUID (PK)        | card identity                              |
| `user_id`     | FK → users.id    | owner, indexed                             |
| `title`       | String(200)      | short headline shown on card               |
| `desc`        | Text             | body text, 2–4 sentences                   |
| `image_url`   | String(512), nullable | OSS URL after upload; null = emoji fallback |
| `image_prompt`| Text, nullable   | prompt sent to Seedream (for debugging)    |
| `category`    | String(32)       | `"diet"` or `"fitness"`                   |
| `status`      | String(16)       | `queued` / `ready` / `red_cut`            |
| `red_cut_at`  | DateTime, nullable | set when user red-cuts this card          |
| `created_at`  | DateTime         | auto-set                                   |

Status lifecycle: `queued` → `ready` (generation complete) → `red_cut` (user rejected).

Pool query: `SELECT * FROM recommendation_cards WHERE user_id=? AND status='ready' ORDER BY created_at ASC LIMIT N`

### `vector_docs` table (existing, extended)

Existing columns: `id`, `source`, `content`, `embedding` (1536-dim), `created_at`.

New column added: `category` String(64), nullable — used for pre-filtering during retrieval (e.g., `grains`, `protein`, `vegetables`, `fat`, `salt`, `exercise`).

Requires an Alembic migration to add the `category` column to the existing `vector_docs` table.

Dietary guidelines chunks stored with `source="dietary_guidelines_2022"`.

## 3. API Endpoints

All endpoints require JWT auth (`CurrentUser`).

### `GET /api/v1/banners?count=N`

Returns up to N `ready` cards for the current user.

After fetching, counts total `ready` cards for the user. If `total_ready < POOL_THRESHOLD (8)`, fires `ensure_pool` as a `BackgroundTask` (non-blocking). Cards stay `status=ready` after being served — they are only consumed (removed from the pool) when the user red-cuts them.

**Response:**
```json
{ "code": 0, "data": [{ "id": "uuid", "title": "...", "desc": "...", "image_url": "https://oss/...", "category": "diet" }] }
```

If pool has fewer cards than requested, returns however many are available.

### `PUT /api/v1/banners/{card_id}/red-cut`

Sets card `status = red_cut`, records `red_cut_at = now()`.

Fetches the next available `ready` card (if any) to return to the frontend for immediate append to the carousel bottom.

Fires `ensure_pool` as a `BackgroundTask` to generate one replacement.

**Response:**
```json
{ "code": 0, "data": { "card": { "id": "...", "title": "...", "desc": "...", "image_url": "...", "category": "..." } } }
```
`card` is `null` if no ready card is currently available.

### `POST /api/v1/banners/init`

Called once on app open. Checks pool size; if `ready count < POOL_THRESHOLD (8)`, fires `ensure_pool` as a `BackgroundTask`. Returns immediately.

**Response:** `{ "code": 0 }`

## 4. Generation Pipeline

### Pool constants

```python
POOL_THRESHOLD = 8   # target ready card count per user
```

### `ensure_pool(user_id, db)`

```
ready_count = COUNT WHERE user_id=? AND status='ready'
deficit = POOL_THRESHOLD - ready_count
if deficit > 0:
    generate_cards(user_id, deficit, db)
```

### `generate_cards(user_id, count, db)`

1. Load user body context via existing `format_user_body_context(user)`.
2. Load last 7 days intake logs and burn logs for the user.
3. Load red-cut card titles: `SELECT title FROM recommendation_cards WHERE user_id=? AND status='red_cut'`.
4. Build a retrieval query string summarizing the user's recent nutrition/activity patterns.
5. Call `rag_service.retrieve(query, top_k=5)` → top-5 dietary guideline chunks.
6. Call Qwen LLM with the full prompt (see Section 5) → JSON array of `count` card drafts.
7. For each draft:
   - INSERT `recommendation_card` with `status=queued`.
   - Call Seedream-4.0 API with `image_prompt`.
   - Download image bytes → upload to OSS.
   - UPDATE card: set `image_url`, `status=ready`.
   - If image/OSS step fails: set `image_url=null`, `status=ready` (emoji fallback).

## 5. RAG — 2022 Chinese Dietary Guidelines

### Embedding model

DashScope `text-embedding-v2`, 1536-dim (matches existing `EMBEDDING_DIM = 1536`).

### Chunking strategy — structure-aware

Chunk by section boundary: one chunk per recommendation block (a complete principle or sub-rule). Oversized blocks (> 600 tokens) are split at paragraph boundaries with 1–2 sentence overlap. Chunks vary in size but each represents a complete, self-contained recommendation.

Each chunk is tagged with a `category` from: `grains`, `vegetables`, `fruits`, `protein`, `dairy`, `fats`, `salt_sugar`, `exercise`, `hydration`, `general`.

### Ingestion script (`scripts/ingest_dietary_guidelines.py`)

- Idempotent: checks for existing `source + content` before inserting to avoid duplicates on re-run.
- Reads the guidelines from a local file (`docs/dietary_guidelines_2022.txt` or PDF).
- Embeds each chunk via DashScope, inserts into `vector_docs`.

### Retrieval (`rag_service.retrieve`)

1. Build a short query string from the user's recent log summary (e.g., `"高脂肪摄入，蛋白质偏低，本周运动不足"`).
2. Embed the query via DashScope `text-embedding-v2`.
3. Filter `vector_docs` by relevant categories derived from user's log profile using these rules: if avg daily fat > 35% of kcal → include `fats`; if avg daily protein < 15% of kcal → include `protein`; if burn logs are empty for 3+ days → include `exercise`; if sodium-heavy foods present → include `salt_sugar`; always include `general`. At least 2 categories are always selected.
4. Cosine similarity search (`<=>` pgvector operator), `LIMIT 5`.
5. Return the `content` text of the top-5 chunks.

## 7. Frontend Integration

### `src/api/banner.js`

```javascript
getBanners(token, count)    // GET /api/v1/banners?count=N
redCutBanner(token, id)     // PUT /api/v1/banners/{id}/red-cut
initBannerPool(token)       // POST /api/v1/banners/init
```

### Home screen

- On mount: call `initBannerPool` (fire-and-forget), then `getBanners(token, 5)` to populate initial carousel.
- `onRedCut(slotIndex)`: call `redCutBanner(token, items[slotIndex].id)`. If `data.card !== null`, update state: `setBanners(prev => [...prev.filter((_, i) => i !== slotIndex), data.card])`. BannerCarousel's `n > prev` effect animates the new card sliding in from bottom-right.

### `GlassCard` image rendering (small change)

```javascript
// before: <Image source={item.image} />
// after:
item.image_url
  ? <Image source={{ uri: item.image_url }} style={g.imgFill} resizeMode="cover" />
  : item.image
    ? <Image source={item.image} style={g.imgFill} resizeMode="cover" />
    : <Text style={g.emoji}>{item.emoji}</Text>
```

## 8. Error Handling

| Scenario | Behavior |
|---|---|
| LLM content generation fails | Card stays `queued`; deficit persists and retries on next trigger |
| Seedream image generation fails | `image_url=null`, card set to `ready`; frontend shows emoji fallback |
| OSS upload fails | Same as above |
| GET pool empty or short | Return available cards (0–N); frontend renders gracefully (`n===0 → null`) |
| Red-cut on unknown card ID | 404 via `BusinessException` |
| Ingestion script re-run | Idempotent check on `source + content` prevents duplicate chunks |

## 9. Out of Scope

- Push notifications when new cards are ready.
- User ability to save / bookmark cards.
- Cross-user card sharing or trending content.
- Image style preferences.
- Scheduled/periodic background generation (can be added later via cron).
